Cost & Context

Measure a whole task.
Keep the information that helps it finish.

In practice

Make one change you can measure

  1. CostSeparate billing categories and choose a suitable access route.
  2. ContextTrim repeated instructions without losing behavior.
  3. ExerciseCompare correctness as well as tokens.

Use the invoice task throughout. No paid live run is required.

In practice

NeedCheck before choosing

Compare current offers against these requirements. Detailed shopping questions are in reference material.

Count the work

Count each billing category separately

CategoryWhat to record
Uncached inputNew input processed at its applicable input rate.
Cache writes and readsSeparate token counts and the configured cache rates.
Generated outputOutput usage, including billable reasoning where applicable.

Bill = sum of each category’s tokens × its rate, plus any separate tool or service fees.

In practice

High input volume does not identify the largest cost

  • Generated output may use a higher token rate than input.
  • Cached input may be much cheaper than newly processed input.
  • Reasoning, retries, cache writes and tool fees can change the balance.

Use the usage record and elapsed time; a shorter visible answer alone does not prove less computation.

Context quality

Keep the facts that the next decision needs

Keep

The invoice rule, failing case, relevant code, decisions and latest test result.

Summarize or remove

Duplicate file dumps, stale logs and abandoned approaches, once their useful findings are captured.

Watch for missed requirements and repeated work. There is no universal “dumb zone” or safe fill percentage.

Context reference

Inspect what actually enters a request

  • Standing instructions and applicable project rules.
  • Tool definitions and relevant skill content.
  • Retained conversation, selected files and tool results.
  • The current user message.

Use a request inspector or provider token counters for real sizes. Avoid summing overlapping categories.

Make it repeatable

Store the rules needed on most tasks

# Project instructions — illustrative invoice repository - Test with: pytest tests/test_invoice.py -q - VAT rates come from the order record. - Preserve existing assertions; explain test changes. - Ask before changing the stored invoice schema.

Use the instruction-file convention your harness actually loads. Keep standing rules short and specific.

In practice

Shorten the file while preserving its constraints

Before

Long project history, duplicate style advice, VAT rules, test commands and an old incident log.

After

Keep VAT source, rounding rule, test command and schema boundary. Link occasional procedures from a skill.

The acceptance check is unchanged behavior on the same tasks, not the smallest file.

In practice

Choose from the state of the task

Unrelated next task

Start fresh with its own scope and needed project context.

Same task, long history

Summarize the goal, evidence, decisions, failed attempts and next check.

Check what survives compaction. Neither a fresh session nor a summary has zero context cost.

Split the work · subagents

Delegate a question; ask for evidence back

  • Fresh helpers need a self-contained task and relevant inputs. Forks can inherit existing history.
  • Keep intermediate investigation in the helper’s context; return findings with file references.
  • Review the result. Delegation adds coordination cost and does not itself isolate filesystem access.

Example return: VAT calculation locations, the failing path, supporting lines and unresolved questions.

In practice

Find the relevant span, then enough surrounding context

  • Search for the invoice entry point and failing test.
  • Read the function, its callers and relevant rules before editing.
  • Delegate broad investigation only when the returned evidence justifies the overhead.

A repeated read can be useful after a file changes. Diagnose before calling it waste.

In practice

Exercise · compare two versions fairly

10 minutes A: the long instruction file. B: the shorter version. Use identical task inputs, repo state, model and tools. Record: acceptance results, all usage, time and retries. Repeat runs if available; inspect failures before choosing.

Output: a comparison worksheet and one justified decision. A smaller prompt that drops the VAT rule loses.

In practice

Measure, trim, then verify again

  1. Record a baseline task outcome and full usage.
  2. Remove one stale or repetitive instruction group.
  3. Repeat the acceptance cases and keep the change only if the tradeoff holds.

Keep the task evidence with the instruction change.
