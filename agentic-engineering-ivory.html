The invoice task02

A useful task has a finish line

Vague request

“Fix the invoice bug.” The agent has to infer both the rule and what counts as done.

Checkable request

“Apply the VAT rate from the order. Preserve the tests, run the invoice suite, and show the diff.”

Illustrative comparison, not two measured runs. A clearer request makes the result easier to assess; it does not guarantee success.

Our route03

Build a loop you can trust enough to use

  1. Understand the machineryModel → harness → tool result.
  2. Define and check doneAcceptance cases, limits and evidence.
  3. Control the workloadUseful context, measured cost and reusable checks.

One task throughout: correct the invoice total, then verify its CSV export.

The predictor · what an LLM does04

The model generates one token at a time

  • Each step produces a distribution over possible next tokens; decoding chooses one.
  • The prediction depends on learned patterns and the context available to that step.
  • Tool calls are generated output too. A separate program handles their execution.

The animation is a simplified decoding example. It does not describe everything learned during training.

The predictor · attention05

Attention connects information in context

  • Attention layers combine information from token positions with different weights.
  • Supply the VAT rule and relevant code. Availability in context still does not guarantee correct use.

Conceptual diagram: multiple heads and layers contribute. Context is an input you curate, not a literal program.

Model behavior06

More reasoning is a setting to evaluate

Illustrative check, not a hidden reasoning trace: Order: net 100.00; VAT rate 21% Expected total: 100.00 × 1.21 = 121.00 Now check the rule, rounding and implementation.

More deliberation can help, and can add time and cost. Compare supported effort settings on the same acceptance cases.

The machinery07

Three parts, three different jobs

01

Model

Proposes text or a structured tool call.

02

Harness

Builds context, applies permissions and coordinates tool execution.

Client

The terminal, editor or web interface where you inspect and steer the work.

For the invoice task: the model requests a test run; the harness arranges it; the client displays the result.

The machinery08

A tool result becomes evidence for the next step

Illustrative tool exchange — syntax varies by harness model → request: run invoice tests harness → execute permitted command in test environment tool → exit 1; expected 121.00, got 100.00 model → inspect the VAT calculation; propose a patch

A tool request is a proposal to execute. Permissions and the tool environment determine what actually happens.

Hands · client & server09

The harness supplies context for each call

Illustrative API-backed loop. History may be sent again, referenced through a stateful API, or compacted; it is not permanent model memory.

The loop · the inner loop10

Keep going, with a limit and a stop condition

  • The harness returns tool results so the model can choose the next step.
  • A verifier checks the candidate result. Failed checks can trigger another attempt.
  • Stop on success, exhausted budget, repeated failure or a required human decision.

For the invoice fix: at most three repair attempts, then report evidence and unresolved failures.

Define done11

A green check proves only what it checks

01

Behavior

VAT comes from the order; zero VAT and rounding cases pass.

02

Integrity

Existing tests remain meaningful. Inspect changed assertions and test discovery.

03

Acceptance

Review the diff and exported values against the task, including gaps in coverage.

Exit code 0 is useful evidence. It is not proof that the full task is correct.

Define done12

Match each failure to a control

FailureConcrete control
Repeats the same failed repairLimit attempts; require a new hypothesis before retrying.
Weakens tests to make them passReview the test diff; run independent acceptance checks.
Changes unrelated behaviorScope allowed paths; inspect the complete diff.

Prompts help communicate these rules. Enforce the important boundaries in tools, permissions and review.

The invoice task13

Make the acceptance contract explicit

GOAL: export invoice net, VAT and gross values to CSV. SCOPE: invoice export code; preserve existing tests. VERIFY: pytest tests/test_export.py -q CASES: 21% VAT, zero VAT, rounding, quoted CSV fields. LIMIT: three repair attempts; then stop and report. EVIDENCE: diff, command, exit status, failures and gaps.

Pair this request with an enforced runtime budget and a review of the resulting artifact.

The bill · context growth14

A short message can carry a long history

ILLUSTRATIVE — three requests, including history

Count the work15

Count each billing category separately

CategoryWhat to record
Uncached inputNew input processed at its applicable input rate.
Cache writes and readsSeparate token counts and the configured cache rates.
Generated outputOutput usage, including billable reasoning where applicable.

Bill = sum of each category’s tokens × its rate, plus any separate tool or service fees.

The bill · KV cache · how17

Caching reuses work on a matching prefix

  • A prompt cache can reuse computed state for eligible, matching earlier content.
  • Keep reusable instructions stable. Changes can invalidate the affected prefix and later content.
  • Inspect cache usage records: expiry, minimum length and provider rules affect whether you get a hit.

Animation shows prefix reuse. Its price label is illustrative; rates vary. Cached content still occupies context.

Context quality18

Keep the facts that the next decision needs

Keep

The invoice rule, failing case, relevant code, decisions and latest test result.

Summarize or remove

Duplicate file dumps, stale logs and abandoned approaches, once their useful findings are captured.

Watch for missed requirements and repeated work. There is no universal “dumb zone” or safe fill percentage.

Split the work · subagents19

Delegate a question; ask for evidence back

  • Fresh helpers need a self-contained task and relevant inputs. Forks can inherit existing history.
  • Keep intermediate investigation in the helper’s context; return findings with file references.
  • Review the result. Delegation adds coordination cost and does not itself isolate filesystem access.

Example return: VAT calculation locations, the failing path, supporting lines and unresolved questions.

Model choice20

Measure the task, including the failed attempts

01

Same acceptance bar

Use representative invoice cases and the same permissions and tools.

02

Whole run

Record quality, elapsed time, all token categories, retries and review effort.

03

Repeat and compare

Repeat representative cases before changing the default configuration.

A higher-priced model can finish in fewer attempts. Whether it costs less is a measurement, not a rule.

Model choice21

Escalate when the evidence points to a need

  1. Start: use a configuration that has met the acceptance bar on similar work.
  2. Diagnose: missing facts, a broken tool and hard reasoning call for different fixes.
  3. Compare: try supported effort or model changes against the same checks and budget.

There is no universal “effort first” ladder. Re-evaluate defaults when the task or model changes.

Split the work22

Assign a role and a return contract

Worker

Implement the bounded invoice change. Return the diff, test output and known gaps.

Reviewer

Check the tax rule, changed tests and edge cases. Return findings with evidence and severity.

Choose configurations from measured performance in each role. A second model’s opinion is not a verifier.

Split the work · dynamic workflows23

One workflow for the invoice change

  • Explore: independently inspect the rule, calculation and export path; return evidence.
  • Plan and build: reconcile findings, then give one owner the implementation.
  • Verify: run acceptance checks and inspect the diff. Retry only within the remaining budget.

Pass evidence between stages. Parallelize independent investigation; coordinate edits and integration.

Make it repeatable25

Store the rules needed on most tasks

# Project instructions — illustrative invoice repository - Test with: pytest tests/test_invoice.py -q - VAT rates come from the order record. - Preserve existing assertions; explain test changes. - Ask before changing the stored invoice schema.

Use the instruction-file convention your harness actually loads. Keep standing rules short and specific.

Make it repeatable27

Connect a few procedures with explicit outputs

Input: invoice defect.
Output: rule, scope and acceptance cases.

02

Implement and check

Input: accepted plan.
Output: patch, tests and unresolved issues.

03

Review and record

Input: patch and evidence.
Output: reviewed result and a reusable lesson.

Teach the workflow through its outputs. Add a new skill only when a repeated need justifies it.

Make it repeatable28

Package useful checks for the team

Skill

The repeatable invoice-check procedure and supporting files.

Plugin or shared package

A versioned way to distribute the procedure and supported integrations.

Test discovery and behavior in a clean session before sharing. Installation does not replace review or permission boundaries.

Take it back to work29

Give the next task a checkable finish

  1. Define done: name the behavior, scope, acceptance cases and stop limit.
  2. Keep evidence: inspect the diff and actual check results; report what remains unverified.
  3. Measure and reuse: record total task cost, then save the check you repeat.
