In practice

Two separate design decisions

Orchestration

Who gets a task, what it depends on and who integrates the result.

Isolation

What files, credentials, processes and network endpoints the tools can access.

A dashboard or Git worktree does not by itself enforce a security boundary.

In practice

Choose from the bottleneck

BottleneckUseful capability
Too many sessions to trackA monitor with task state and evidence links.
Independent changes collideSeparate workspaces plus explicit file ownership.
Ready work waits unclaimedA queue with leases, retries and review gates.
Tools can touch too muchA restricted environment with scoped credentials.

Choose products only after these requirements are clear.

In practice

One ticket, explicit state transitions

Ready: invoice rule + scope + acceptance cases Claimed: one owner + lease + retry budget Working: permitted workspace + progress evidence Review: patch + checks + unresolved gaps Accepted: reviewer confirms the requested behavior

Failed or blocked work returns with evidence. A green tool run does not automatically publish a change.

In practice

Specify the environment the worker receives

  • Allow the repository paths and commands required by the ticket.
  • Scope credentials and network access to the necessary services.
  • Use separate edit workspaces; enforce time, attempt and spend limits outside the prompt.

Review mounts, egress and permissions in the actual runtime.

Define done

Match each failure to a control

FailureConcrete control
Repeats the same failed repairLimit attempts; require a new hypothesis before retrying.
Weakens tests to make them passReview the test diff; run independent acceptance checks.
Changes unrelated behaviorScope allowed paths; inspect the complete diff.

Prompts help communicate these rules. Enforce the important boundaries in tools, permissions and review.

In practice

Write a verification skill you can test

10 minutes Define the trigger: invoice or CSV export changes. Write four checks: VAT, zero VAT, rounding, escaping. Name the command and required evidence. Test with one matching task and one unrelated task.

Output: a small skill file and evidence that it is used when appropriate.

In practice

Compare the complete interaction

MCP

Tools exposed through a client/server protocol, with structured inputs and supported authentication paths.

CLI

Commands executed by a shell tool, with help, arguments, output and error handling.

Both can reach local or remote services. Both need appropriate credentials, permissions and review.

In practice

Definitions are only one part of the cost

  • MCP schemas may be loaded eagerly or discovered on demand, depending on the client.
  • CLI use also consumes shell definitions, help text, command output and repair attempts.
  • Compare successful completion, tool failures, total usage and latency.

Measure the actual client configuration. There is no universal cheaper interface.

In practice

Run the same read through both interfaces

Task: retrieve the invoice ticket and its acceptance cases. Hold data, access scope and requested output constant. For CLI and MCP, record: correctness; calls; failures; tokens; elapsed time Repeat after warm-up; report missing measurements.

This is an experiment design, not a completed case study.

In practice

Design the return and the review before fan-out

  • One owner per task and a clear integration point.
  • Enforced boundaries and a finite retry budget.
  • Evidence-bearing returns, checked against the original acceptance cases.

Choose interface and orchestration tools from observed needs.
