In practice

Separate the case, the grader and the trial

Test case

Export a net-100 invoice with 21% VAT.

Grader

Parse the CSV and check that net, VAT and gross are 100, 21 and 121.

Trial

One fresh attempt with a recorded model, prompt, tools and environment.

Evaluate the resulting artifact. A message saying “done” is not the outcome.

5
In practice

Use the strongest practical check for each claim

Deterministic check

Parse CSV, assert values and run regression tests.

Written rubric

Assess explanation quality and completeness against named criteria.

Human calibration

Check ambiguous cases and compare model-judge scores with human decisions.

A different judge model does not remove bias. Blind labels and vary answer order where practical.

6
In practice

One success answers a different question

Illustrative outcomes for one case: fail fail pass fail fail At least one success in five attempts: yes All five attempts successful: no Observed single-attempt success rate: 1 / 5

This small sample does not establish production reliability. Report task coverage, repeats and uncertainty.

7
In practice

Record the observable run

  • Inputs, configuration, tool requests, results and timestamps.
  • Final files or external state, check output and exit statuses.
  • Usage categories, retries, failures and any unavailable evidence.

Telemetry is not a full transcript, and neither guarantees access to hidden model reasoning.

A repeated step is a question to investigate

Observed stepWhat to ask
Read calc.py; edit it; read it againDid the second read inspect the changed code?
Repeat a failed tool callDid the environment or arguments change?
Restate the plan after a handoffDid this restore missing requirements?

Label a step waste only after checking its purpose and effect.

Model choice

Measure the task, including the failed attempts

Same acceptance bar

Use representative invoice cases and the same permissions and tools.

Whole run

Record quality, elapsed time, all token categories, retries and review effort.

Repeat and compare

Repeat representative cases before changing the default configuration.

A higher-priced model can finish in fewer attempts. Whether it costs less is a measurement, not a rule.

14
In practice

Active parameters are not the RAM requirement

  • Stored weights depend on total parameters, representation and quantization.
  • Inference also needs a KV cache, activations, runtime buffers and overhead.
  • Offloading can move weights to CPU memory or disk, trading memory for transfer time.

Approximate weight storage: parameters × bits per weight ÷ 8. This is a lower-bound estimate, not a fit guarantee.

16
In practice

Choose from constraints and observed results

Local may fit

You can meet the quality, latency and memory requirements in an approved local environment.

Hosted may fit

Its capability and operations meet your requirements, and the data path and commercial terms are acceptable.

Inspect the whole workflow: local inference does not stop tools or telemetry from using the network.

17
In practice

Review dictated requirements before execution

Spoken: “Export invoices without changing stored records.” Check the transcription for: - negation: WITHOUT changing records - exact file names and amounts - scope and permission boundaries

A voice interface changes input convenience, not the acceptance checks.

18
In practice

Change one thing and keep the acceptance bar

  • Choose representative cases and calibrate the grader.
  • Compare variants on repeated, isolated trials.
  • Inspect failures, then keep the change only if the complete result improves.

Keep separate cases for the final check so prompt tuning does not simply memorize the test set.
