Context: remove outdated rules

Anthropic removed over 80% of Claude Code's system prompt for its Claude 5 generation models. Review your CLAUDE.md too.

3
Context · the number

A shorter prompt, the same scores

>80%

of Claude Code's system prompt deleted for Claude Opus 5 and Claude Fable 5, “with no measurable loss on our coding evaluations.”

  • Their diagnosis: “we were overconstraining Claude Code.”
  • One request combined conflicting rules: “leave documentation as appropriate” and “DO NOT add comments”.
  • Conflicting rules add work. Remove constraints that no longer help.

5
Context · CLAUDE.md

CLAUDE.md: gotchas, not the obvious

  • Say briefly what the repo is for, then “spend most of the tokens on gotchas.”
  • Skip what the repo already shows.
  • Point to a verification skill instead of pasting the procedure.
  • Size: the costs docs suggest under 200 lines. It loads every session.
# Orders API Checkout and invoicing service. ## Gotchas - All types live in one monolithic file. - The subscriptions table is append-only. Use the highest version, not the latest created_at. - Staging returns 200 even when the Stripe webhook didn't process. Check payment_events. ## Verification - Before calling anything done, use the checkout-verifier skill.

Illustrative file based on the posts. Chapter 06 adds a stop rule. Apply the same approach to agent system prompts.

Context · prompt audit

Remove outdated workarounds

  • “Instructions written for an older model can make Opus 5.5 write more and repeat tool calls.”
  • Review thinking prompts, retry workarounds, rigid procedures and duplicate checks.
  • Run /claude-api prompt-audit: it audits skills, CLAUDE.md and app code.
  • One benchmark (44 support tickets): Opus 4.8 to Opus 5.5 at low effort -18% cost, the audit a further -9%. An example, not a promise.
Using Claude Code

Remove “think hard” and “think step by step” from saved prompts. Check whether quality holds.

Building agents

Remove old workarounds, rerun evals, then compare effort levels.

Skills · structure

Organize files, scripts and hooks

  • Start with SKILL.md. Link to references, assets and runbooks so Claude can load them as needed.

Prompt cache · the numbers

Higher cache hit rates lower costs

5%

A cached read costs 5% of a fresh input token (Opus 5.5).

$11.20 → $1.62

Same 2.8M input tokens: uncached vs 90% cache hits. At 96%, about $0.99.

$0.02 vs $0.60

Read vs write at 120K context. An expired cache turns the next read into a write.

Example: a 40-turn task growing from 20K to 120K context. Cache lifetime in Claude Code: 1 hour on a subscription, 5 minutes on an API key or cloud provider.

14
Prompt cache · compaction

Compact with the same prefix

  • A separate summary call can charge full price for the conversation.
  • Fork with the same prefix. Append the summary request as a user message.
  • Claude Code at 150K: compaction costs ~$0.25, saves ~$0.025 a turn, pays back in ~10 turns. Right before finishing, it costs more than it saves.
  • /compact keep the failing test names and the schema change. Tell it what to keep.

Verification & evals · ratchets and guardrails

Measure progress. Prevent regressions.

The lab metric

Use repeatable measurements: instruction counts, React commits, style recalculations and DOM mutations.

The CI guardrail

“A number that could only ratchet down.” A daily job lowers the ceiling. Valgrind counts: -48% and -31% instructions, -78% and -44% wall-clock.

  • Keep a benchmark only if improving it produces real speed gains.
  • Guardrails first: tests before optimizations, automated review plus one human approval, feature flags, staged rollout (employees, 1%, everyone).
  • About a third of PRs added telemetry or guardrails.

Verification & evals · prompts to steal

Check the change. Report what is unverified.

Real check, before “done”
Before reporting done, run a test, build, type-check or command that exercises the change. Syntax checks and commands that fail to start don't count. If no real check can run, state what remains unverified and why.
Review before a human
Review this branch against main. List merge blockers only: file, line, reason and how to reproduce.
Mark the unknowns
Mark anything you couldn't confirm, and say where you looked.

Four checks for your eval

PropertyWarning sign
Mirrors productionTasks chosen because they're easy to generate or grade
Scales with model and thinkingDoesn't? “ambiguous tasks or a miscalibrated grader”
HeadroomTop model at top effort near 100%, or a task that fails every run

  • Graders: programmatic first. Else an LLM judge with a rubric of checkable claims, not a 1-to-5 scale, and not the model under test.
  • Pick hard cases because a human judged them hard, not because today's model fails them.
  • “Read a sample of scored transcripts before believing your evaluator.”
  • Start: claude update, then /claude-api build-eval.

06

Define done and when to stop

Early testers ran Opus 5.5 on long coding tasks “for hours with little oversight”.

25
Autonomy · done and stop

Define the result. Set a stop rule.

One message, one finish line
Migrate the payment endpoints from the old client to the new one. Done means: every endpoint uses the new client, the old client is deleted, and the test suite passes. Stop and ask me only if a test fails for a reason you can't explain.
CLAUDE.md stop rule
When a step doesn't need my input, keep going. Put status notes in the same message as your next action. Stop and ask only when you can't continue without me, or before anything destructive: deleting data, force-pushing, or changing anything outside this repository.

Keep permission prompts on for destructive commands. Pair-programming instead? Ask for the opposite: a one-line plan before, a short recap after. Mid-run addition: type a follow-up and press Enter.

Autonomy · files and handoffs

Keep state in a file. Read the handoff first.

Task list that survives compaction
Keep a checklist in TASKS.md. Tick each item when it's done, and add anything new you find.
A handoff you can scan
End every run with three headings: Blocked on me, Changed, Found.
One subagent per service
Audit every service in services/ for the retry bug in the linked issue. Give each service to its own subagent. When a subagent reports back, check its evidence before you accept it. Finish with one table: service, affected yes or no, and the evidence.

When a long run ends, read what it needs from you first. Read the file, not the scrollback.

Autonomy · what humans do

What humans still decide

Ambition

“By default, Claude is careful about scope. It tickets findings, hedges on feasibility, and pads its estimates.” Say “please be braver.”

Taste

One human owner per thread reviews before-and-after recordings and decides user-visible tradeoffs.

Direction

One benchmark per thread. Humans prioritize, merge and stop work when gains become too small.

Example verdict: “2ms per send is not worth the complexity of maintaining this build plugin.” Standing instructions in the channel: a role, responsibilities, and the goal “become as autonomous as possible.”

07

Separate contexts must earn their cost

Separate contexts can help with incomplete work, biased reviews and lost requirements. They also cost tokens.

28
Multi-agent · failure modes

Three ways a single context fails

  • Incomplete work. Stops after partial progress and declares done: 35 of 50 items in a security review.
  • Biased self-review. Prefers its own results when asked to verify them.
  • Goal drift. After compaction: “Each summarization step is lossy.” Edge cases and don't-do-X rules get lost.
  • Use subagents with separate contexts and focused goals.

A dynamic workflow is a JS file using agent(), parallel(), pipeline(). Ask for one, or say “ultracode”. “Best practices are still developing.”

29
Multi-agent · the six patterns

Six workflow patterns

Classify-and-act

Classify the task, then route it to the right agent.

Fan-out-and-synthesize

Split the work across fresh contexts. Wait for all results, then combine them.

Adversarial verification

A separate agent verifies each output against a rubric.

Generate-and-filter

Generate ideas, test them, remove duplicates and keep the best.

Tournament

N agents attempt the same task differently. A judging agent compares them pairwise.

Loop until done

Repeat until a stop condition is met, such as no new findings.

Multi-agent · prompts

Four prompts you can paste

Loop until done · competing theories
This test fails maybe 1 in 50 runs. Set up a workflow to reproduce it. Form competing theories about the race, and don't stop until one theory survives the evidence.
Mine your own sessions
Using a workflow, go through my last 50 sessions and mine them for corrections I keep making and turn the recurring ones into CLAUDE.md rules
Adversarial verification
Go through my blog post draft and verify every technical claim against the codebase using a workflow, I don't want to ship anything wrong.
Generate-and-filter · tournament
I need a name for this CLI tool. Use a workflow to brainstorm a bunch of options and run a tournament to pick the top 3.

Sorting 1,000+ items? Don't sort in one prompt. Run pairwise comparisons: “comparative judgment is more reliable than absolute scoring.”

Harness · tool design

Revisit your tools every model generation

AskUserQuestion

A dedicated question tool shipped on the third attempt. It pauses the loop until answered.

Todos to Tasks

Old reminders made Claude stick to the list. Better models needed more flexible task tools.

Vector DB to Grep

“The most consequential tools we've built are the ones that let Claude find its own context.”

The Guide subagent

Docs search runs in a subagent and returns only the answer, keeping the main tool list small.

Harness · output format

Ask for HTML. End with an export.

The author's personal opinion
  • “I find it difficult to read a Markdown file of more than a hundred lines.”
  • Sliders and knobs, then a copy-as-prompt button: “always to end with an export.”

Using Claude Code

Name specific design patterns to avoid. “Avoid a generic look” gives little direction.

Example list

No cream or off-white background, italic accent words in headings, numbered “01 / 02 / 03” labels, monospace labels, pill-shaped buttons.

Harness · mods

Mods: observe, rewrite, answer

on("tool.call", { tool: "Bash" }, async ($, e, next) => { const risk = classify(String(e.command ?? "")); if (risk === null) return next(e); ... return { deny: `Blast Radius held this command: ...` }; });
  • Observe: await next(e). Rewrite: next({...e}). Answer: return without calling next.
  • You needn't know the API. Prompt: “Make me a Claude Code mod called token-weather…” Hot reload does the rest.
  • Blast Radius is “a safety net, not a permission system.” Use permission rules for a hard block.
  • Read the mod's repo before installing it.
