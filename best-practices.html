In practice

Start with three changes

Instructions

Remove conflicting or obsolete rules; preserve real constraints.

Verification

Make done depend on evidence tied to the task.

Measurement

Compare configurations by outcomes, cost and review effort.

Skills, caching and delegation support these three habits.

Reported by Anthropic

Your next step

Remove one obsolete instruction group, then rerun your own acceptance cases.

15
Model choice

Escalate when the evidence points to a need

  • Start: use a configuration that has met the acceptance bar on similar work.
  • Diagnose: missing facts, a broken tool and hard reasoning call for different fixes.
  • Compare: try supported effort or model changes against the same checks and budget.

There is no universal “effort first” ladder. Re-evaluate defaults when the task or model changes.

16
Model choice

Measure the task, including the failed attempts

Same acceptance bar

Use representative invoice cases and the same permissions and tools.

Whole run

Record quality, elapsed time, all token categories, retries and review effort.

Repeat and compare

Repeat representative cases before changing the default configuration.

A higher-priced model can finish in fewer attempts. Whether it costs less is a measurement, not a rule.

In practice

Ask for evidence tied to the changed behavior

Before calling the invoice fix done: 1. Run the invoice acceptance cases. 2. Inspect changed assertions and the final diff. 3. Check the exported CSV values. 4. Report commands, exit statuses, failures and gaps.

A syntax check cannot establish the VAT calculation. A command that never starts is not a passed test.

Improvement target

19
In practice

Use the strongest practical check for each claim

Deterministic check

Parse CSV, assert values and run regression tests.

Written rubric

Assess explanation quality and completeness against named criteria.

Human calibration

Check ambiguous cases and compare model-judge scores with human decisions.

A different judge model does not remove bias. Blind labels and vary answer order where practical.

In practice

Keep some cases out of prompt tuning

  • Develop on cases that expose known failures.
  • Hold back different invoice variants for the final comparison.
  • Inspect grader mistakes and near-duplicate cases before celebrating a score.

A better development score is evidence to investigate, not proof of general improvement.

21
The invoice task

Make the acceptance contract explicit

GOAL: export invoice net, VAT and gross values to CSV. SCOPE: invoice export code; preserve existing tests. VERIFY: pytest tests/test_export.py -q CASES: 21% VAT, zero VAT, rounding, quoted CSV fields. LIMIT: three repair attempts; then stop and report. EVIDENCE: diff, command, exit status, failures and gaps.

Pair this request with an enforced runtime budget and a review of the resulting artifact.

Separate durable task state from delegation

TASK STATE Goal; completed work; evidence; unresolved work; next check. HELPER TASK One scoped question; relevant inputs; permitted actions; required findings with evidence and uncertainty.

A new worker reads the handoff, verifies the current state, then continues.

Scope

Decide what outcome and tradeoffs are worth pursuing.

Authority

Acceptance

Review the result against requirements and user-visible behavior.

In practice

Use separate contexts for a clear reason

Investigate and combine

Independent questions; evidence-bearing returns; one integration owner.

Build and review

One worker produces a patch; a separate reviewer checks it against a rubric.

A second agent can miss the same issue. Keep deterministic checks and final acceptance.

25
In practice

Two checks before adding workers

Will it help?

Estimate coordination and review effort; measure cost per accepted result.

What may it touch?

Configure filesystem, network and credential boundaries independently of context separation.

Enforce budgets in the harness. A token budget written in a prompt is a request, not necessarily a hard cap.
