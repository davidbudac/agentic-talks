In practice

When to reach for a subagent

Use one for

Read-heavy exploration

Findings without the raw material.

Independent parallel work

Streams that never need each other.

Noisy output

Test runs, logs, long docs.

Skip it for

Quick lookups

The setup costs more than the answer.

Tightly shared state

Every hand-off loses detail.

Edits to the same files

Subagents can’t coordinate.

In code

On the API, a subagent is another call

subagent.py
def run_subagent(task):
resp = client.messages.create(
model=MODEL,
max_tokens=2048,
system=SUBAGENT_SYSTEM,2
messages=[{"role": "user",
"content": task}],1
cache_control={"type": "ephemeral"},
)
return resp.content[0].text3
1

A fresh message list. The task is all it knows.

2

The same system prompt for every subagent, so it can be cached.

3

Only the final text goes back to the lead.

Takeaways

What to take back to your team

Delegate

Subagents buy a clean lead and parallel time with tokens.

Brief

Write a self-contained task and name the return format.

Order

Stable first, volatile last; the prefix must match exactly.

Share

One cached prefix makes fan-out cheaper. Warm it first.
