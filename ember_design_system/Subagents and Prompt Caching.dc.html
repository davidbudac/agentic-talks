Subagents

Isolated, parallel work with their own context windows — funnelling results back to a coordinating lead.

The big idea

It's like handing a job to a helper

You stay on the main task. A helper goes off, does the messy digging on its own, and brings back just the answer.

The trade in the design

Subagents are mutually invisible

Sub A has no idea Sub B exists. All cross-talk routes through the lead — the sole integration point. Any shared state must be re-passed explicitly on each spawn.

The economics

Tokens for clean context — a real trade

YOU PAY
Every subagent re-pays a fixed cost — its own system prompt and task setup — and the orchestration itself burns tokens.
YOU WIN WHEN
Isolated work would otherwise pollute the lead enough to degrade reasoning — or parallelism saves wall-clock time.

For a trivial lookup, a subagent is pure overhead. For deep multi-file research, it pays for itself.

In practice

When to reach for a subagent

Use it for
+Read-heavy exploration — findings without the raw material
+Independent, parallel streams of work
+Work that would otherwise pollute the lead's window
Skip it for
−Trivial lookups — pure overhead
−Tasks that need tightly shared state
−Many agents writing the same files — they can't coordinate
In code

A subagent is just another call

No special primitive — a fresh messages.create with its own message list.

def run_subagent(task):
    resp = client.messages.create(
        model=MODEL, max_tokens=400,
        system=SUBAGENT_SYSTEM,  # shared, cached prefix
        messages=[{"role": "user",
                "content": task}],  # the ONLY thing it knows
    )
    return resp.content[0].text  # ← the single block that crosses back

Prompt Caching

Store a prefix of context so repeat requests skip re-processing it — cheaper and faster.

The big idea

Read it once — not every time

Picture answering several questions about the same long document. Re-read it every time — or read it once and remember?

The one catch

Only if nothing changed

The shortcut holds only while the remembered part stays exactly the same. Change something early, and it's a brand-new read.

Reuses what it already read — no re-reading.

Caching is server-side — the computed prefix lives in the cloud beside the model. Your harness only flags where to cache; nothing is stored on your machine.
The core idea

Reuse the prefix, recompute the rest

The start of your context is often identical across requests. Cache its computed state once; later requests load it instead of recomputing.

What actually gets cached

Not text — computed state

You mark a breakpoint with cache_control. Everything from the start of the request up to and including that block becomes the cache key.

}

Under a subscription

Subscription OAuth vs an API key — drawing the line for automation.

The big idea

Who's doing the talking?

It comes down to one question. A subscription is for you using Claude yourself; an API key is for your programs to use it on their own.

YOU at the keyboard
Using Claude yourself — including through the official Claude Code tool.
→ a subscription fits
>_ your programs
Scripts and automations calling on their own, with no one at the keyboard.
→ give them an API key
The only real no-no: dressing a program up as you to dodge the line.
OAuth & subscriptions

Allowed vs. not allowed

The line is about which client makes the call — not the auth mechanism itself.

✓Allowed
API key for SDK & automation
The sk-ant-api… key from the Console — no automation limits.
The real Claude Code CLI
Run claude under your plan — local, cron, CI on your own repo.
✕Not allowed
OAuth tokens in your own script
Extracting a subscription token to call api.anthropic.com yourself.
…or in third-party clients
Consumer-plan OAuth in other tools violates the terms — actively enforced.
What to do instead

Two legitimate paths

NEED THE API SURFACE
Use an API key
From the Console. No automation restrictions. The code runs identically — only the credential source changes.
WANT A FLAT-RATE CAP
Run inside Claude Code
Shell out to claude -p. Stays on your subscription, inside the official harness — caching managed for you.

Caveat: this policy area has been volatile — check the current usage policy page before you architect around it.

Key takeaways

What to carry out of the room

01
Subagents trade tokens for clean context + parallelism. Use them for read-heavy, independent work.
02
The task string must be self-contained; the return must be explicitly shaped.
03
Caching reuses an exact prefix: stable content at the front, volatile at the back.
04
They compound — a shared, cached prefix makes fan-out cheap.
The through-line

Both protect the lead's context.

One by isolating work. One by reusing it.
