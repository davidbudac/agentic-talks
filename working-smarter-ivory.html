In practice

One success answers a different question

Illustrative outcomes for one case: fail fail pass fail fail At least one success in five attempts: yes All five attempts successful: no Observed single-attempt success rate: 1 / 5

This small sample does not establish production reliability. Report task coverage, repeats and uncertainty.

In practice

Record the observable run

  • Inputs, configuration, tool requests, results and timestamps.
  • Final files or external state, check output and exit statuses.
  • Usage categories, retries, failures and any unavailable evidence.

Telemetry is not a full transcript, and neither guarantees access to hidden model reasoning.

Count the work

Count each billing category separately

CategoryWhat to record
Uncached inputNew input processed at its applicable input rate.
Cache writes and readsSeparate token counts and the configured cache rates.
Generated outputOutput usage, including billable reasoning where applicable.

Bill = sum of each category’s tokens × its rate, plus any separate tool or service fees.

Split the work · subagents

Delegate a question; ask for evidence back

  • Fresh helpers need a self-contained task and relevant inputs. Forks can inherit existing history.
  • Keep intermediate investigation in the helper’s context; return findings with file references.
  • Review the result. Delegation adds coordination cost and does not itself isolate filesystem access.

Example return: VAT calculation locations, the failing path, supporting lines and unresolved questions.

In practice

Two separate design decisions

Orchestration

Who gets a task, what it depends on and who integrates the result.

Isolation

What files, credentials, processes and network endpoints the tools can access.

A dashboard or Git worktree does not by itself enforce a security boundary.

In practice

One ticket, explicit state transitions

Ready: invoice rule + scope + acceptance cases Claimed: one owner + lease + retry budget Working: permitted workspace + progress evidence Review: patch + checks + unresolved gaps Accepted: reviewer confirms the requested behavior

Failed or blocked work returns with evidence. A green tool run does not automatically publish a change.

In practice

Specify the environment the worker receives

  • Allow the repository paths and commands required by the ticket.
  • Scope credentials and network access to the necessary services.
  • Use separate edit workspaces; enforce time, attempt and spend limits outside the prompt.

Review mounts, egress and permissions in the actual runtime.

Define done

Match each failure to a control

FailureConcrete control
Repeats the same failed repairLimit attempts; require a new hypothesis before retrying.
Weakens tests to make them passReview the test diff; run independent acceptance checks.
Changes unrelated behaviorScope allowed paths; inspect the complete diff.

Prompts help communicate these rules. Enforce the important boundaries in tools, permissions and review.

Write a verification skill you can test

10 minutes Define the trigger: invoice or CSV export changes. Write four checks: VAT, zero VAT, rounding, escaping. Name the command and required evidence. Test with one matching task and one unrelated task.

Output: a small skill file and evidence that it is used when appropriate.

In practice

Compare the complete interaction

MCP

Tools exposed through a client/server protocol, with structured inputs and supported authentication paths.

CLI

Commands executed by a shell tool, with help, arguments, output and error handling.

Both can reach local or remote services. Both need appropriate credentials, permissions and review.

In practice

Definitions are only one part of the cost

  • MCP schemas may be loaded eagerly or discovered on demand, depending on the client.
  • CLI use also consumes shell definitions, help text, command output and repair attempts.
  • Compare successful completion, tool failures, total usage and latency.

Measure the actual client configuration. There is no universal cheaper interface.

In practice

Active parameters are not the RAM requirement

  • Stored weights depend on total parameters, representation and quantization.
  • Inference also needs a KV cache, activations, runtime buffers and overhead.
  • Offloading can move weights to CPU memory or disk, trading memory for transfer time.

Approximate weight storage: parameters × bits per weight ÷ 8. This is a lower-bound estimate, not a fit guarantee.

In practice

Estimate storage, then list what is missing

10 minutes — illustrative hardware scenario 35B total parameters; 3B active per token; four-bit weights. Weight-only storage ≈ 35B × 4 / 8 = 17.5 GB. Would a machine with 16 GB available memory fit it? What could offloading change? What must you measure?

Output: a qualified feasibility note. Include KV cache, buffers, quantization overhead and speed.
